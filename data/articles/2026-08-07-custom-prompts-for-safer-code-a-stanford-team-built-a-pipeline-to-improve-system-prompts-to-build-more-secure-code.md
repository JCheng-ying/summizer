# Custom Prompts for Safer Code: A Stanford team built a pipeline to improve system prompts to build more secure code
https://www.deeplearning.ai/the-batch/custom-prompts-for-safer-code-a-stanford-team-built-a-pipeline-to-improve-system-prompts-to-build-more-secure-code/

这篇文章讨论的是 AI 写代码这件事里一个容易被"能不能写出漏洞"这个更醒目的问题盖过去的另一面:大语言模型不仅会漏掉安全问题,它自己写出来的代码本身就经常带着安全漏洞——而且原文的关键洞察是,单纯在提示词里加一句"请写安全的代码"基本没用。

文章指出,斯坦福团队(Houjun Liu、Lisa Einstein、John Jang 等)做了一套叫 SecureForge 的方法,自动优化编程模型的系统提示词(system prompt),目标是在不牺牲代码质量的前提下降低生成代码里的安全漏洞率。核心思路分几步:先用一个 LLM(GPT-5.4)基于 MITRE CWE(一套软件安全常见错误分类目录)里排名前 25 的漏洞类型,生成听起来很正常、用户可能真的会问的编程需求(比如把"SQL 注入"这个漏洞类型,转成"写一个通过用户名在 SQLite 数据库里查用户的 Python 函数"这种看起来无害的请求);把这些请求喂给待测的编程模型,用静态代码分析工具 Semgrep 自动检测输出代码有没有漏洞;把确实会触发漏洞的请求留下来,再让模型对这些请求做变体扩写,扩到 8 万条;最后用一种叫 GEPA 的遗传算法,反复迭代改写系统提示词——每一轮把 Semgrep 发现的具体漏洞位置反馈给 GPT-5.4,让它提出改进后的系统提示词,直到提示词没法再明显改善为止。

文章给出的结果是,这套方法在 CodeLlama、Qwen2.5-Coder、Qwen3、Kimi K2、Claude Sonnet 4.6、GPT-5.3 Codex、GPT-5.4 系列等多个模型上做了测试:平均下来,SecureForge 生成的代码里有安全漏洞的比例是 11.8%,而单纯在提示词里要求"写安全代码并列出要避免的问题"这种朴素做法,漏洞率是 20.1%——大约是两倍的差距。具体到 GPT-5.4,朴素提示下漏洞率 15.8%,SecureForge 降到 10.1%;GPT-5.4 Mini 从 21.4% 降到 12.4%;GPT-5.4 Nano 从 22.1% 降到 15.6%。文章也提示了局限:这套方法只针对已知的漏洞类型做了优化,对未知类型漏洞的防御效果还是个开放问题。

个人看法:这篇文章和几天前那篇"Claude 攻破 HAWK"报道其实是同一个大主题的两个不同侧面,原文自己也点出了这层联系——Anthropic 的 Claude Mythos 5 因为能发现严重的软件漏洞而备受关注,展示了 AI 在安全防御上的潜力,但原文提到 Mythos 5 自己的系统卡里也记录过它错误宣称"已验证"、或者漏掉/忽视软件里重要问题的情况。也就是说,同一代模型,既可能是"最强的漏洞发现者",也可能是"漏洞的制造者"——这两种能力并不是自动画等号或者自动互斥的关系,分析安全能力时不能一概而论,要分别看"审查已有代码找漏洞"和"自己写代码时会不会带出漏洞"这两件事。

个人看法:这类"给模型定制系统提示词来提升安全性"的方法论,本质上是把安全能力从"依赖模型本身天生有多强",变成了"能不能用工程化的流程把安全要求灌输进模型的默认行为"——这对**AI 板块**里做编程助手/Agent 框架的公司是一个值得关注的信号:如果 SecureForge 这类方法能被打包成产品化的服务(比如某种"企业级安全系统提示词优化"工具,直接卖给用编程助手的企业客户),会是一个独立于底层模型能力之外的、可以单独收费的价值层,类似此前 RoboReward 那类"专门解决某个具体薄弱环节"的技术路径——不是去做更大更强的模型,而是精确地补上现有模型的某个具体短板。值得跟踪这类系统提示词优化技术后续会不会被具体的编程助手厂商采纳或收购。
