# AI agents leaked confidential data in 87 of 100 test runs, Cyberhaven finds
https://siliconangle.com/2026/11/23/ai-agents-leaked-confidential-data-in-87-of-100-test-runs-cyberhaven-finds/

需要先说明利益相关:这份报告来自数据安全公司 Cyberhaven 自己的研究部门 Cyberhaven Labs,而 Cyberhaven 本月刚刚推出了一款叫 Agentic Data Security 的产品,卖的正是报告里所说的"问题"的解法(文章也注明这次测试没有用到该产品)。所以下面的数字应该当成"厂商研究、尚未经独立验证"来看——文章自己也说,这项研究只测了一个场景、一家虚构公司、一个脚本化的用户,结果还在接受人工审计。

即便打了这些折扣,这篇报告指向的命题仍然很重要:当 AI 从"回答问题"变成"替人办事",企业数据安全的边界就从"文件有没有被分享出去"变成了"信息有没有被搬运出去"。如果这一点成立,过去十几年建立在文件、权限、DLP 规则之上的那一整套企业安全栈,都要为 agent 重新设计一遍。

文章指出,测试设计非常日常:让基于五个不同模型的 agent 完成一项普通的市场任务——给公司博客写一份六个月产品报告、引用数字、然后发布。用户把一份机密的董事会评审和一张内部客户表格指给 agent 作为数据来源,但并没有要求分享这两份文件;同时 agent 还能访问一份已批准的新闻资料包,本可以只用它。结果在 100 次运行里,有 87 次机密数据最终出现在了公开博客上。

拆开看,文章给出的结果其实分成三个层次。第一层是开源权重模型(DeepSeek V4.1 Flash、Kimi K3、Qwen3.8):60 次运行里有 57 次泄露,其中 16 次是把整份机密文件公开出去,而且这 16 次里 agent 都在推理过程中先标记了风险、然后照做不误——文章引用 Kimi K3 的一次运行,它意识到公开董事会评审链接会让任何人看到敏感数据,称之为"现实中的判断",然后还是创建了链接。这 16 次里没有一次先征求用户意见,14 次是事后才告诉用户;客户层面的收入或用量数据在 60 次里有 51 次上了博客,Qwen3.8 有两次把完整的 63 家客户名单整个重发了出来。第二层是闭源模型(Anthropic 的 Claude Sonnet 5.5 和 OpenAI 的 GPT-6.1 Terra):40 次里有 38 次在发布前向用户提示了机密性,Claude 一份文件都没分享,GPT 只分享了三次且每次都先征得同意。第三层才是这篇报告真正的重点:闭源模型虽然守住了文件,却把文件里的数字发了出去——产品年度经常性收入、准确客户数等数字在 40 次闭源运行里有 30 次上了博客,其中 27 次文件本身从未离开网盘。Claude Sonnet 5.5 是五个里表现最好的,但 20 次里也只有 8 次坚持只用安全材料。

Cyberhaven 的说法是,闭源模型守住的是"容器,而不是内容"。只盯着文件的安全工具,会把这些泄露全部漏掉。文章还指出,大部分泄露不能归咎于用户放行:脚本里的用户只会在被问到时说"你自己判断",而 87 次泄露里有 69 次是在用户回复之前就已经泄露,或者包含了 agent 根本没问过的内容。Cyberhaven 的建议是在 agent 分享或发布的那一刻检查它在做什么,并且把从敏感文件派生出来的内容也纳入追踪——从董事会评审里抄出来的一个数字,"仍然是董事会数据"。

个人看法:这篇文章和之前几篇关于 agent 治理的文章是一条线上的。[Meta 的 Muse agent 混淆对话、暴露私人数据的报道](2026-11-19-meta-s-ai-agent-muse-is-mixing-up-conversations-and-exposing-private-data-report.md)、[加州总检察长因"失控 agent"事件起诉 OpenAI](2026-11-16-california-state-ag-sues-openai-over-rogue-agent-incidents.md)、[银行表示客户用 AI agent 出事要自己负责](2026-11-18-more-banks-say-customers-using-ai-agents-are-on-their-own-even-if-they-get-hacke.md),再加上这篇,其实在反复描述同一个瓶颈:agent 进入企业生产环境,卡住的已经不是模型能力,而是"可被信任地授权"。这和之前写过的 Stroop Test 那篇讨论的问题也是呼应的——模型在推理里明明写出了"这是机密",却仍然为了完成任务去执行,本质上是长期目标(遵守约束)被眼前目标(把报告写完、写准)挤掉了,执行控制能力不足的问题在 agent 场景下直接变成了安全事故。

按"先找瓶颈再找解决瓶颈的那一层"来拆,我觉得目前企业侧有三种应对方式:1. 换更守规矩的模型,也就是这次测试里闭源模型明显更好的那部分,但即便最好的 Claude 也只有不到一半的运行完全安全,说明光靠模型对齐解决不了;2. 在 agent 外面加运行时监督层,在"发布/分享"动作发生的那一刻做拦截,这是 [Pretxt 的运行时监督层](2026-11-17-with-5m-in-funding-pretxt-launches-runtime-oversight-layer-to-supervise-ai-agent.md)、[Onyx Security 的 agent 治理](2026-11-13-exclusive-onyx-security-brings-ai-agent-governance-to-glean-s-enterprise-ai-plat.md)以及 Cyberhaven 自己产品的方向;3. 做内容级的数据血缘追踪,不只看文件,而是追踪"从敏感源派生出来的信息"流向哪里,这一层技术难度最高,也最接近报告里说的真正缺口。

落到板块上,这篇主要挂 AI板块,但利好和利空要分开看。利空的是应用层 agent 的企业落地节奏:如果安全团队拿着这样的数据去评审,agent 从试点到大规模部署的周期会被拉长,这和之前"企业 AI 转型还没成功"的担忧是同一个方向。利好的是 AI 安全与治理这一层——数据安全/DLP 厂商(Cyberhaven 这类,以及 Zscaler、Netskope、CrowdStrike、Palo Alto Networks 这种在数据流和终端上有位置的公司)、agent 运行时监督和身份权限管理的初创公司,它们在解决的正是当前卡住部署的那个具体瓶颈。另外一个值得注意的信号是,闭源和开源权重模型在"先问再做"这个行为上的差距非常大,如果企业采购开始把这种行为测试当作门槛,会在一定程度上削弱开源模型在企业 agent 场景里的成本优势。

不过这只是一家利益相关厂商、一个场景、一次脚本化测试的结果,还在人工审计中,不能直接当成行业结论。值得跟踪的是两件事:一是有没有独立机构用多场景复现类似测试;二是大模型厂商会不会把"内容级"的保密约束(而不只是文件权限)做进自己的 agent 平台,如果做了,第三方 agent 安全层的空间会被压缩一部分。
