# AgenticASR Incorporates User Corrections to Edit Speech Recognition on the Fly
https://www.deeplearning.ai/the-batch/agents-come-to-speech-recognition/

这篇文章讲的是一项语音识别方面的研究,但它触及的问题其实比"语音转文字准不准"更根本——当语音输入变成一个持续多轮交互的过程,而不是一次性转录,系统应该怎么处理用户的纠正,这个设计思路本身可能比这次的具体基准分数更有参考价值。

文章指出,上海交通大学、浙江大学、复旦大学以及微软旗下小冰公司的研究者提出了 Agentic ASR——把自动语音识别(ASR)引擎和一个专门检测、纠正转录错误的 LLM 配对起来,在每一轮对话里都尝试修正。文章点出了现有方案的一个核心问题:多数系统处理错误的方式是把 ASR 模型和一个改写输出的 LLM 搭配使用,但纠正的时候只是简单地把用户的纠正请求追加到已有转录文本后面,让 LLM 从头改写整段转录风险很大,尤其是遇到发音相近但拼写不同的专有名词时(比如把 Megan 听成 Morgan)。文章提出,如果把纠正过程拆成三步——找到错误的位置、理解用户到底想说什么、应用修改——LLM 就能更像一个编辑而不是一个重写者去处理这类问题。

具体工作流程上,系统先用语音转文字引擎(Qwen3-ASR-1.7B)生成初步转录,再用一个 LLM(Qwen3-32B)结合已有转录结果做优化;这个 LLM 会把用户的输入分成三类意图——确认(用户接受当前结果)、新增(用户想继续补充内容)、纠正(用户想修改已有内容)。确认和新增不会改变已有转录,只有纠正才会触发编辑:LLM 会先定位需要修改的具体片段,再判断用户想改成什么(比如"不,我说的是 Megan,不是 Morgan"),然后执行这个修改。文章提到,由于现有的多语言语音转文字基准里没有"用户纠正输出"这类样本,研究者用一个 LLM 加文字转语音引擎去模拟用户口述再纠正的完整过程,并提出了一个叫 S²ER 的新指标,专门衡量转录结果未能保留说话人原意的比例。结果显示,多轮交互能持续降低语义错误,而且大部分提升发生在最初几轮:在 GigaSpeech 基准上,S²ER 从第 0 轮的 21.5% 降到第 10 轮的 3.5%;在包含大量人名地名的 AISHELL-NER 基准上,S²ER 从 19.9% 大幅降到 2.0%,命名实体错误率从 2.4% 降到 1.2%;在中英文混合的 ASRU2019 基准上,S²ER 从 28.6% 降到 1.4%。

个人看法:这篇文章值得和之前的[Treble 声学交互观点文章](2026-08-16-why-robots-that-can-t-communicate-naturally-won-t-be-adopted.md)放在一起看——那篇讨论的是机器人在嘈杂真实环境里语音交互能力的普遍缺失,这篇文章提供的正好是解决这个问题里的一块具体拼图:把语音识别从"一次性转录"变成"可持续多轮修正的交互过程"。用"先找瓶颈"的方法看,语音交互此前的瓶颈之一是专有名词、口音、混合语言这类"一次性转录几乎必然出错"的场景,而 Agentic ASR 提出的三步拆解(定位-理解-修改)恰好针对的是这类最容易出错、也最需要人工干预纠正的场景,这个设计思路本身具备跨场景的通用性——文章结尾也提到,这套"定位要改哪里、理解要改成什么、执行修改"的流程,同样可以套用到编辑文档、审查代码、迭代设计这类需要交互式修正的任务上,而不只是语音识别。对 **AI 板块** 和 **机器人板块** 而言,这类"agent 化"的底层交互范式一旦验证有效,直接受益的会是需要处理语音输入的产品层(智能音箱、车载语音、人形机器人的语音交互模块),因为它提供了一个不需要每次都从零重新转录、成本更低的纠错路径;对 **edge AI 板块** 也有间接意义——如果这类多轮修正能在更小的本地模型(比如 Qwen3-32B 这个量级)上跑通,意味着语音交互这类高频交互场景不一定需要依赖云端大模型才能做到可靠的纠错体验。现在这项研究还停留在基准测试和模拟用户交互的阶段,没有看到具体产品化的时间表,值得持续关注这套三步拆解方法会不会被现有的语音助手或人形机器人公司采纳落地。
